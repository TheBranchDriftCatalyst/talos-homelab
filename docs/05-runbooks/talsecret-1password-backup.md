# Backing up the Talos secrets bundle to 1Password

## TL;DR

1. Confirm `configs/talsecret.yaml` is present and complete.
2. Confirm git cannot see it.
3. Copy it into a 1Password Secure Note named `talos-secrets-bundle`.
4. Read it back out of 1Password. A backup you have not read back is not a backup.
5. Clear your clipboard.

A copy was made on 2026-08-24 under that item name (TALOS-w04r). Re-run this whenever the
secrets bundle changes, or when you want to confirm the stored copy is still readable — the
verify step is the one worth repeating on its own.

---

## What this file is, and why it matters

`configs/talsecret.yaml` holds the cluster's **identity**:

|                                 |                                                             |
| ------------------------------- | ----------------------------------------------------------- |
| 5 certificate authorities       | `os`, `k8s`, `etcd`, `k8s-aggregator`, `k8s-serviceaccount` |
| `cluster.id` / `cluster.secret` | what makes this _this_ cluster                              |
| machine token                   | lets a node join                                            |
| k8s bootstrap token             | lets a node register with the API server                    |
| secretbox encryption secret     | encrypts secrets at rest in etcd                            |

**Anyone holding this file can mint a node into your cluster.** It is gitignored and must
stay that way.

It is also **irreplaceable**. Lose it and you cannot regenerate a node that the existing
cluster will accept — every CA would differ, so etcd would reject the new member and kubelet
would fail TLS to the API server. The only recovery is rebuilding the cluster from scratch and
restoring workloads from Velero and CNPG backups.

For a long time exactly **one copy existed**, on one laptop, untracked. That is the situation
this runbook exists to end, and the reason step 6 (read it back) is not optional.

## Step by step

### 1. Open a terminal in the repo

```bash
cd ~/catalyst-devspace/workspace/talos-homelab
```

### 2. Confirm the file is there and looks right

```bash
ls -la configs/talsecret.yaml
grep -c "crt:" configs/talsecret.yaml     # expect 4
```

If `ls` says no such file, **do not run `talhelper gensecret` with no arguments, and do not
run `talosctl gen secrets` with no input flag.** Either one mints a BRAND NEW certificate
authority. That does not recover the cluster — it defines a different one. Every existing
kubeconfig and talosconfig stops working and no surviving node can rejoin etcd.

Recover it instead. It can be EXTRACTED, losslessly, from any control-plane machine config
you still have — a file in `configs/clusterconfig/`, a backup, or one pulled off a live node:

```bash
cd configs
talhelper gensecret -f clusterconfig/catalyst-cluster-talos00.yaml > talsecret.yaml
```

Verified: run against this cluster, that reproduces every value in the existing
`configs/talsecret.yaml` exactly — all four certificates, all five keys, the cluster ID,
the bootstrap token, and the secretbox encryption secret.

Note the circularity, though: `configs/clusterconfig/` is _generated from_ `talsecret.yaml`.
If you have neither the bundle nor any control-plane machine config anywhere, this does not
save you — that is precisely why the 1Password copy exists.

### 3. Confirm git cannot see it

```bash
git check-ignore -v configs/talsecret.yaml
```

You want output naming `.gitignore`. **If you get NO output, stop** — the file is not ignored
and must not be committed. Tell me and I will fix it before you continue.

### 4. Copy the contents

```bash
cat configs/talsecret.yaml | pbcopy
```

That puts the whole file on your clipboard. (`pbcopy` is macOS built-in; nothing to install.)

### 5. In the 1Password app

1. Click **New Item** → choose **Secure Note**
2. **Title:** `talos-secrets-bundle`
3. In the note body, press **⌘V** to paste
4. Add these fields (click _add more_ → _text_), so future-you knows what this is without
   opening it:
   - `cluster` → `catalyst-cluster`
   - `talos-version` → whatever `talosVersion:` currently says in `configs/talconfig.yaml`
   - `extracted-from` → `configs/talconfig.yaml` (declarative source; configs generated by talhelper)
   - `date` → today's date
   - `purpose` → `Talos machine config identity. Required to regenerate node configs. Cluster is UNRECOVERABLE without this.`
5. Put it in whichever vault your other infrastructure secrets live in — the same one as
   `nexus-admin`, so it is found by whoever looks for infra credentials
6. **Save**

### 6. Verify you can read it back

In 1Password, open the item and check the note starts with `cluster:` and contains
`bootstraptoken`. **Do not skip this** — a backup you have not read back is not a backup.

### 7. Clear your clipboard

```bash
pbcopy < /dev/null
```

## The admin client config — a second credential, and this one expires

`configs/talsecret.yaml` is the cluster's identity and never expires. The **admin client
config** is a different thing with a different failure mode, and it lives in the same vault:
a 1Password **Document** named `talos-admin-talosconfig`, in vault `catalyst-eso`.

Stored 2026-11-06, verified by checksum against the local file. Restore it with:

```bash
op document get talos-admin-talosconfig --vault catalyst-eso --out-file talosconfig
```

(Named rather than written as a `op://…` URI on purpose — gitleaks flags that scheme, and the
rest of this file names items the same way.)

**It expires.** `talosctl config new` issues a client certificate with a default TTL of one
year. The copy stored above runs to **2027-11-06**. When it lapses, every `talosctl` call
fails — including `etcd members`, which is how the cold-boot script decides whether the
cluster came back. Its failure message reads _"etcd only reached 0/3 … DO NOT bootstrap"_,
so an expired certificate presents as a catastrophic etcd failure and invites exactly the
wrong repair.

This was caught on 2026-11-06 with **three days to spare**, during an audit of the shutdown
scripts rather than by anything watching for it. Nothing alerts on it.

### Renewing it

```bash
talosctl -n 192.168.1.54 config new /tmp/talosconfig.new --roles os:admin --crt-ttl 8760h
```

Then verify before replacing anything — the old one keeps working until it lapses, so there
is no reason to overwrite an untested file:

```bash
TALOSCONFIG=/tmp/talosconfig.new talosctl -n 192.168.1.54 etcd members
```

### THERE ARE TWO COPIES, and the second one is the trap

| Path | Used by |
| ---- | ------- |
| `configs/talosconfig` | the scripts and every `task talos:*` (they set `TALOSCONFIG`) |
| `~/.talos/config` | **every `talosctl` you type by hand**, because that is the fallback when `TALOSCONFIG` is unset |

Renewing only the repo copy leaves the scripts working and every interactive command dying on
the old certificate — the same outage through a different door. Merge into the global config
too, and make it current:

```bash
talosctl --talosconfig ~/.talos/config config merge /tmp/talosconfig.new
talosctl --talosconfig ~/.talos/config config context admin@catalyst-cluster
```

Confirm with `talosctl config info` **with `TALOSCONFIG` unset** — that is the path a human
actually exercises.

## What NOT to do

- **Do not** email it, Slack it, or put it in a note app.
- **Do not** commit it, even to a private repo. Git history is forever and this file has no
  business in any repo.
- **Do not** store it only on this laptop. A single copy on one disk is the situation this
  runbook exists to end.
- **Do not** paste it into an AI chat, including me. I do not need to see it to do any of this
  work, and I have never read its contents — only checked which keys are present.

---

## Why not automate this?

The obvious candidate is ESO, and it is the wrong tool in a specific way: ESO reaches 1Password
through a Connect server running _in the cluster_. This secret is what you would need in order to
REBUILD that cluster, so a mechanism that requires the cluster to be up cannot be the mechanism
that protects it.

That circularity is the real reason this stays manual. A bootstrap secret must be recoverable
without the thing it bootstraps — so even with the `op` CLI available, the copy that matters is
the one a human can retrieve from a phone while the cluster is dead.
